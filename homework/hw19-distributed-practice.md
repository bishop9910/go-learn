## 1. 背景与目标

从「单机并发」跨到「多节点一致性」。本作业要求动手实现三个分布式基础组件中的两个（第三个加分），每一项都要有可运行实现、测试与报告。

三个任务分别是：简化版 Raft（选举 + 日志复制 + 持久化）、分布式锁（Redis 与 etcd 两条路线）、一致性哈希（虚拟节点 + 数据迁移）。评分重点在**正确性论证与故障注入测试**，而不是「跑起来没报错」。

## 2. 需求（必须项）

1. MUST 从任务 A、B、C 中完成两项（第三项自愿，计入加分）；每项都要有实现、测试与报告章节。
2. MUST 所有代码通过 `go test -race -count=1 ./...`，且必须有超时与取消（任何等待都不能是无限的）。
3. MUST 用 `log/slog`（见 <https://pkg.go.dev/log/slog>）输出关键事件：选举开始/结束、角色变化、日志提交、锁获取/释放、节点增删；日志带节点标识，便于观察时序。
4. MUST 任务 A（简化版 Raft）：实现单机多节点的内存 KV 存储，节点间通信可用进程内 channel 或真实 TCP（推荐 TCP）。
5. MUST 任务 A 包含 Leader 选举：term、投票、多数派判定、随机化选举超时；并说明随机化区间的取值理由。

9. MUST 任务 B（分布式锁，两条路线都要实现并对比）：Redis 路线使用 `SET NX PX` + 唯一 value + Lua 原子释放 + watchdog 续期；etcd 路线使用租约 + 事务 + revision。
10. MUST 任务 B 处理「锁过期而业务未完成」：给出 fencing token 或版本校验方案，并说明为什么单纯续期不足以解决。
11. MUST 任务 B 如实分析 Redis 主从切换导致锁失效的场景，并给出应对（至少说明为什么「能用幂等就不用锁」）；同时提供一个幂等实现作为对照。
12. MUST 任务 B 的测试包含 100 并发争抢场景，断言「同一时刻只有一个持有者」（用持有者计数器 + 临界区检测实现）。
13. MUST 任务 C（一致性哈希）：实现带虚拟节点的哈希环，支持增删节点。

## 8. 提示与思路

- 选举最容易踩的坑是「所有节点超时相同」：必须为每个节点在其区间内独立随机，并在每次选举失败后重置随机值。
- 多数派判定用「超过半数」而不是「半数」：3 节点需要 2 票，5 节点需要 3 票。
- 日志提交只应由 Leader 推进 `commitIndex`，并随下一次 `AppendEntries` 把新值带给 Follower；Follower 不能自行推断提交。
- 持久化字段的选择原则是「重启后不能再做出与已承诺状态矛盾的决策」，因此 term 与 votedFor 是关键，其次是 log。
- 分布式锁的本质问题是「持有者以为自己还持有，但锁已经过期」。因此要么保证操作幂等，要么引入单调递增的 fencing token 让被保护资源自己拒绝旧持有者。
- 一致性哈希的迁移比例可以用「先记录 key → 节点 的映射，再加一个节点，比较映射变化的 key 数量占比」来测；虚拟节点数太少会导致负载比明显偏离 1。
- 报告中的正确性论证建议按「安全性（不会出现两个 Leader 同时提交）」与「活性（最终能选出 Leader）」两条线分开写。

## 9. 常见坑

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| 选举超时全节点相同 | 反复同时竞选，无法选出 Leader | 每节点独立随机区间，失败后重新随机 |
| term 不持久化 | 重启后重复投票，可能选出两主 | term 与 votedFor 必须落盘后再回复 |
| 只更新 Leader 的提交位置 | Follower 永远读不到新数据 | 提交位置由 Leader 推进并随复制请求下发 |
| 多数派用 `len/2` | 3 节点 2 票即通过（错误地允许平票场景） | 使用严格过半 |
| 锁释放不校验持有者 | 误删他人锁 | 释放时校验唯一 value，用原子脚本执行 |
| 虚拟节点数过小 | 负载严重倾斜、迁移量异常 | 每节点分配足量虚拟节点并给出均衡度数据 |
| 并发下 map 竞争 | `-race` 报错或数据损坏 | 加锁或改用 channel 传递所有权 |
| 测试不注入故障 | 容错能力从未被验证 | 必测分区、宕机、重启三类场景 |
| 用真实时钟做时序断言 | 偶发失败，CI 不稳定 | 拉长容差或用 `testing/synctest` |

## 10. 参考实现要点

- Raft 节点状态机骨架（仅示意字段与流转，完整逻辑自行实现）：

```go
type Role int // Follower / Candidate / Leader

type Node struct {
	mu       sync.Mutex
	term     int
	votedFor string
	log      []Entry
	commit   int
	role     Role
}
// 关键流转：心跳超时 -> Candidate -> 获多数票 -> Leader；发现更高 term -> Follower
```

- 事件日志统一字段：`node`、`term`、`role`、`event`、`detail`，用 `log/slog` 输出；演示脚本靠这些事件还原时序。
- 分区模拟的两种做法：真实 TCP 下用「丢弃发送 + 拒绝连接」模拟；进程内实现下用可控的消息队列开关模拟。两种都必须保证「分区期间不产生跨分区的状态同步」。
- 锁的临界区检测方法：进入临界区时用原子计数器加一，断言其值为 1；退出时减一；该断言在 100 并发下重复执行若干轮。
- fencing 思路：被保护资源在每次写入时校验携带的 token 是否大于已见过的最大值，否则拒绝；这样即使旧持有者延迟到达也无法造成破坏。
- 一致性哈希环的数据结构要点：哈希值有序排列，查找时取「第一个大于等于 key 哈希的节点」，环形回绕；虚拟节点是把节点标识与序号拼接后再哈希。
- 与成熟实现的差距应具体写：例如缺少成员变更协议、缺少快照与日志压缩、缺少批量与流水线优化、缺少客户端线性一致读等。
