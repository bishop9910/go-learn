## 1. 背景与目标

hw13 的两个服务已经能被直接访问，hw14 让它们可见。现在缺一层把外部流量收敛起来的入口：统一鉴权、统一错误、统一超时，以及在压力下保护后端的限流与熔断。本作业用 `net/http/httputil.ReverseProxy` 写一个网关雏形，把流量按路径转发到 hw13 的两个服务。

目标：

1. 网关能按配置化路由表转发，并正确处理请求标识与转发头，且不信任客户端伪造的头。
2. 限流在单机与集群两个层面都能生效，超限返回 429 并带 `Retry-After`。
3. 下游持续故障时熔断器打开，快速失败而不是把网关的 goroutine 全部耗光。
4. 依赖不可用时有明确的降级路径，网关仍返回可用响应。
5. 一个慢下游不能拖垮整个网关，隔离手段可解释、可验证。

## 2. 需求（必须项）

**M1 反向代理实现。** 用 `net/http/httputil.ReverseProxy` 实现按路径前缀转发到 `user-service` 与 `post-service`。**必须使用 `Rewrite` 而不是 `Director`**：`Director` 在 Go 1.26 起废弃，原因是它无法阻止客户端通过 hop-by-hop 头（例如 `Connection` 里列出的头）删除代理添加的头，恶意客户端可借此清除转发链上的标识。README 必须写出这段原因并标注版本。

**M2 路由表配置化。** 路由规则（路径前缀、目标服务名、超时、限流键类型、是否鉴权）从文件或配置中心读取，不硬编码在代码里；配置变更后按 hw12 的热更新通路生效，白名单外的项改动不生效。

**M3 请求标识。** 为每个请求生成请求 ID 并透传到下游，响应里回带。客户端已带请求 ID 时的处理策略要明确（接受或忽略），并说明为什么。

**M4 统一鉴权。** 网关统一校验 token：或调用 `user-service` 校验，或用共享密钥本地校验 JWT。鉴权失败的响应格式与其他错误一致；校验结果可缓存时说明缓存键与失效策略。

**M5 统一错误响应。** 所有错误（鉴权失败、限流、熔断、超时、下游 5xx、找不到路由）返回同一结构的 JSON，含机器可读的错误码与请求 ID；不得把下游的错误栈或内部地址泄漏给客户端。

**M6 超时与取消。** 网关到下游的调用有显式超时，客户端的取消信号沿 `ctx` 透传到下游；说明超时时间与下游自身超时的层次关系（谁应该更长）。

**M7 转发头与信任边界。** 正确处理 `X-Forwarded-For` 与 `X-Request-ID`：只有在请求来自可信代理时才沿用客户端传入的 `X-Forwarded-For`，否则一律重写并追加可信来源；`X-Request-ID` 需要长度与字符集校验。README 用一节写清信任边界与伪造风险。

**M8 限流算法。** 三种算法至少实现两种并对比：固定窗口（要指出临界问题：窗口边界两侧的突发可以放过接近两倍配额）、滑动窗口、令牌桶（允许突发）。README 给出对比表。

**M9 单机与分布式限流。** 单机用 `golang.org/x/time/rate`（模块路径，以官方最新稳定版为准，具体 API 以包文档为准）；分布式用 Redis + Lua 脚本实现原子令牌桶，说明为什么必须用脚本保证「读令牌数 → 计算 → 写回」的原子性。

**M10 限流键与响应。** 限流键支持按用户、按 IP、按接口三种，并说明各自的适用位置与失效场景（例如按 IP 在 NAT 后会把无关用户算在一起）。超限返回 429，响应带 `Retry-After`，其取值来源与算法一致。

**M11 熔断状态机。** 实现三态熔断器（closed / open / half-open），基于滑动窗口统计失败率与慢调用比例；给出阈值配置与恢复试探策略（试探请求数、成功判定、再次打开的条件）。说明熔断与重试的相互作用：重试会放大故障，重试必须限制在熔断器内部且限制次数与总时长。

**M12 降级。** 定义至少两条降级路径（例如推荐位返回空列表、作者信息返回兜底值），并写测试证明依赖不可用时网关仍返回 200 且结构合法的响应。降级响应必须带标识，便于统计降级比例。

**M13 隔离。** 为不同下游配置独立的连接池与并发上限；README 说明「一个慢下游拖垮整个网关」的机制（共享连接池耗尽、goroutine 堆积、上游队列排队）以及隔离如何阻断它。

**M14 观测接入。** 把限流拒绝数、熔断状态变化、下游延迟接入 hw14 的指标与看板；标签基数遵守 hw14 的禁止清单。熔断状态变化必须同时产生一条日志。

**M15 测试。** 覆盖三类：限流算法单测（含时钟推进，**优先用 Go 1.25 转正的 `testing/synctest` 做虚拟时间测试**，`synctest.Test` / `synctest.Wait`；Go 1.27 另有 `testing/synctest.Sleep`）；熔断状态机单测（构造失败序列，断言状态迁移时机）；网关端到端测试（用 `net/http/httptest` 起假下游，覆盖转发、鉴权、超时、限流、熔断五条路径）。

**M16 压测报告与 README。** 给出压测报告：在设定阈值下的实际 QPS、429 比例、P99 延迟与熔断触发点。README 含架构图与决策表：什么情况下限流、什么情况下熔断、什么情况下降级。

## 8. 提示与思路

1. **先写路由与转发，再加保护。** 网关的中间件顺序建议固定为：请求 ID → 访问日志与指标 → 鉴权 → 限流 → 熔断 → 降级 → 代理。顺序错了会出现「被限流的请求也计入了熔断失败率」这类统计污染。
2. **限流键要能解释。** 每个限流规则都要能回答「为什么是这个人/IP/接口」，否则配额被谁吃掉永远说不清。
3. **熔断器的滑动窗口用桶而不是全量记录。** 固定数量的时间桶把内存占用变成常数，代价是统计有桶粒度的误差，这个误差要写进设计说明。
4. **重试放在熔断器内部。** 重试在外层意味着熔断器只看到一次最终失败，失败统计被稀释；重试在内层则每次尝试都计入统计，且总次数与总时长有上限。
5. **隔离先隔离连接池与并发。** 只加超时是不够的：慢下游会把各自连接池占满，独立池与独立并发上限才是阻断点。
6. **虚拟时间测试是限流单测的最优解。** 用 `testing/synctest` 让时间在测试里瞬时推进，测试不依赖真实等待，也不会因为机器负载而抖动。

## 9. 常见坑

| 坑 | 现象 | 根因 | 正确做法 |
| --- | --- | --- | --- |
| 用 `Director` 且未清理客户端可控头 | 客户端可删除代理添加的转发头，绕过信任链 | `Director` 在 Go 1.26 起废弃即是为此 | 用 `Rewrite`，在改写阶段重置并重设转发头 |
| 限流键取自可伪造的头 | 只要改一个头就能换一个配额桶 | 键来源不受信任 | 键取自可信来源（认证后的用户身份或可信来源 IP） |
| 计数器无界增长 | 内存随时间上涨，最终 OOM | 每个新键都新建计数器且从不淘汰 | 过期淘汰或 LRU 上限 |
| 熔断阈值拍脑袋 | 要么从不触发，要么频繁误触发 | 阈值没有对照真实延迟分布 | 用 hw14 的延迟分位与错误率数据推导阈值 |
| 把重试放在熔断器外层 | 熔断迟迟不打开，故障被不断放大 | 失败统计被重试稀释 | 重试限制在熔断器内部并设总时长上限 |
| 反向代理未限制请求体 | 一个大体积请求把网关内存打满 | 缺少大小上限 | 设置请求体上限，超限直接返回错误 |
| `Response.Body` 泄漏 | 连接无法复用，文件描述符耗尽 | 忘记关闭或未排空 | 处理完立即关闭；必要时读尽再关 |
| 固定窗口限流放在边界上 | 窗口切换瞬间通过接近两倍配额 | 固定窗口的固有临界问题 | 用滑动窗口或令牌桶，并在文档中说明差异 |
| 所有下游共用一个连接池 | 一个慢下游把网关整体拖慢 | 无隔离 | 按下游配置独立连接池与并发上限 |

## 10. 参考实现要点

**为什么必须用 `Rewrite`。** 代理添加的身份与转发头，只有在「代理自己重写请求」的语义下才不会被客户端影响；`Director` 的模型允许客户端通过 hop-by-hop 头把代理添加的头删掉，因此在 Go 1.26 起废弃（见 <https://go.dev/doc/go1.26>）。

```go
// 示意：Rewrite 是 net/http/httputil.ReverseProxy 的字段名
// 具体函数签名与可用方法以官方文档为准：https://pkg.go.dev/net/http/httputil
rp := &httputil.ReverseProxy{
	Rewrite: rewriteFor(target), // 在改写阶段重置转发头，再按信任边界重新设置
}
```

**三种限流算法的取舍。**

| 算法 | 突发处理 | 临界问题 | 状态量 | 适用 |
| --- | --- | --- | --- | --- |
| 固定窗口 | 窗口内可突发到配额上限 | 窗口边界可放过接近两倍配额 | 每键一个计数 + 窗口起点 | 精度要求低、实现最简 |
| 滑动窗口 | 平滑，突发受限 | 需要用前一窗口加权，逻辑略复杂 | 两个窗口计数 + 权重 | 要求平滑拒绝的接口 |
| 令牌桶 | 允许突发到桶容量 | 桶容量设大等于允许长突发 | 令牌数 + 上次填充时间 | API 配额、允许短时突发的场景 |

**熔断状态机的最小骨架。**

```text
closed     : 请求正常放行；滑动窗口内失败率或慢调用比例超阈值 → open（记录打开时间）
open       : 请求快速失败；进入 open 时长超过配置值 → half-open
half-open  : 放行有限数量的试探请求
             ├─ 试探全部成功 → closed（重置窗口统计）
             └─ 任一试探失败 → open（重新计时，并拉长下一次试探间隔）
```

关键设计决策：

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 慢调用判定 | 用延迟分位数阈值而非平均值 | 平均值被快请求稀释，掩盖尾延迟 |
| 窗口形态 | 固定数量时间桶的滑动窗口 | 内存常数，误差可控且可解释 |
| 重试位置 | 熔断器内部 | 每次尝试都计入失败统计，避免故障被稀释 |
| 隔离方式 | 每下游独立连接池 + 并发上限 | 阻断「慢下游占满共享资源」的传导路径 |
| 降级判定 | 熔断打开或超时率超阈值 | 与熔断状态联动，避免两套判定打架 |

压测报告至少包含：并发梯度、实际 QPS、429 比例、P99 延迟、熔断触发与恢复的时间点；数据以表格 + 原始输出文件交付，不要只给一句结论。
