## 1. 背景与目标

把前面作业的散件整合为一个**简历可写**的作品集仓库。评分标准不是「功能多」，而是「面试官 3 分钟内能看懂你解决了什么问题、架构如何分层、有哪些工程亮点、数据指标是多少」。

推荐主线：hw15 网关 + hw13 两个微服务 + hw14 可观测 + hw16 K8s 部署，整合为 `go-backend-portfolio`（或自拟名称）。核心验收要求是「一条命令起全栈」。

## 2. 需求（必须项）

1. MUST 从既有作业中选定一条主线并整合为单一仓库，说明取舍：整合了哪些、放弃了哪些、为什么。
2. MUST `README.md` 包含：架构图、技术选型表与理由、快速开始、演示 GIF 或截图说明。
3. MUST 提供接口契约：`openapi.yaml` 或 gRPC proto，二者与实际实现一致（字段、状态码、错误码可核对）。
4. MUST 提供 `compose.yaml`，一条 `docker compose up -d` 起全栈：应用 + MySQL + Redis + MQ + Prometheus + Grafana + Jaeger 或 OTel Collector。
5. MUST 提供 `chart/` 或 `k8s/` 部署清单，复用 hw16 的成果并保持参数一致。
6. MUST 提供 CI 工作流（构建、静态检查、测试、镜像推送、部署或干跑）。
7. MUST 提供 `Makefile`、`Taskfile` 或 PowerShell 脚本，把常用操作收敛为少数入口命令。
8. MUST 提供压测报告与性能优化报告，性能结论必须引用 hw10 / hw17 的实测数据（注明采集命令）。
9. MUST 提供测试与覆盖率报告，`go test -race ./...` 全绿。
10. MUST 提供 `CHANGELOG.md`，按版本记录变更。
11. MUST `README.md` 满足「3 分钟可读」：开头一段说清业务问题与用户价值，禁止把功能清单当介绍；每条技术亮点必须给出数据或指向报告链接。
12. MUST 至少写出 4 个「可讲的技术点」，每个都能回答三问：为什么这么做、代价是什么、怎么验证。可选方向：缓存一致性与降级、Outbox 幂等消费、容器感知 `GOMAXPROCS` 与 CPU 限流、手写限流熔断、用 pprof 定位到的真实优化。
13. MUST 做一次「从零克隆到跑起来」的干净环境验证：在全新目录或全新容器中严格按 README 操作，记录每一步耗时与踩到的坑，并把坑回写进 README 的 FAQ。
14. MUST 提供 `docs/pitch.md`（5 分钟讲解稿）与高频追问清单（至少 15 问），覆盖并发、GC、一致性、故障处理、性能数据来源。
15. MUST 仓库中不得提交密钥、`.env`、本地绝对路径与个人凭据。

## 4. 技术约束

- Go 版本基线为 Go 1.25（本机 `go1.25.7`）。引用 Go 1.26/1.27 的能力时须标注版本，不得混用于同一份「已验证」结论。
- 第三方依赖只写模块路径并注明「以官方最新稳定版为准」；不得编造版本号。
- 一键启动不得依赖本机手动安装的中间件（除容器运行时外）。
- 所有性能数字必须能追溯到仓库内的脚本与原始输出，禁止出现无出处的指标。
- 报告与 README 一律简体中文，代码标识符与路径保持英文。
- 不得把他人项目代码原样搬入；引用第三方代码须注明来源与许可证。

## 6. 验收标准（可执行命令）

```bash
docker compose up -d
curl -f localhost:8080/healthz
make verify
go test -race ./...
```

PowerShell 等价：

```powershell
docker compose up -d
Invoke-WebRequest -UseBasicParsing localhost:8080/healthz
make verify
go test -race ./...
```

判定标准：`docker compose up -d` 后 2 分钟内所有服务健康；`curl -f` 返回 0；`make verify` 串起契约校验、静态检查与测试且返回 0；`go test -race ./...` 全绿；README 中的每条命令在实际环境中可直接执行。

## 8. 提示与思路

- 整合顺序建议：先让「服务 + 依赖」在 compose 中跑通，再补可观测，再补契约与文档，最后做 CI 与 K8s 清单。反过来做会在文档上反复返工。
- README 的写法可以套三段结构：第一段「问题与方案」（3 句话）、第二段「架构与关键决策表」、第三段「数据与验证」。亮点不要写成形容词，写成「指标：优化前 X → 优化后 Y，采集命令见 …」。
- 技术点的表达模板：现象（观察到什么问题）→ 原因（根因在哪一层）→ 方案（为什么选这个）→ 代价（放弃了什么）→ 验证（哪条命令给出什么数据）。
- 干净环境验证建议用一次性容器或新目录，并强制自己「只看 README、不看源码」；记录每一步的时长，超过 10 分钟的步骤说明文档或镜像有问题。
- FAQ 的题目来源：把 hw17 实验结论、hw18 源码阅读的纠正直觉、hw19 的正确性论证各挑几条改写，这些都是面试高频区。
- 性能优化报告要区分「测出来的」与「推测的」；只写测出来的部分，推测部分单独列成「未验证假设」。

## 9. 常见坑

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| README 写成功能清单 | 面试官看不到重点 | 按「问题 → 架构 → 数据」组织，亮点挂数据 |
| 只在本机跑通 | 换台机器起不来 | 做一次干净环境验证并把坑写进 FAQ |
| 依赖本地手动装的组件 | 一键启动失败 | 全部中间件容器化，镜像固定 tag |
| 指标没有出处 | 数据不可信 | 每个数字附采集命令与原始输出路径 |
| 照抄他人代码 | 讲不清细节，一问就露 | 只引用并注释来源，核心逻辑自己实现 |
| 没有 FAQ | 演示时被一个问题问住 | 至少 15 问，覆盖并发、GC、一致性、故障、数据来源 |
| 仓库提交密钥 | 安全事故 | `.gitignore` + 示例配置，密钥走环境变量或外部注入 |
| 契约与实现不一致 | 联调失败、文档失效 | 契约变更纳入 CI 校验 |
| CHANGELOG 事后补写 | 版本混乱 | 每次合并同一 PR 内更新 |

## 10. 参考实现要点

- `compose.yaml` 的服务划分建议：`app`、`mysql`、`redis`、`mq`、`prometheus`、`grafana`、`jaeger`（或 `otel-collector`）；用健康检查与 `depends_on` 条件保证启动顺序，避免应用启动时依赖未就绪。
- 统一入口命令的最小集合：

```text
make up        # 起全栈
make down      # 停并清理
make verify    # 契约校验 + vet + test -race
make bench     # 压测并输出对比表
make load-test # 生成演示数据
```

- 可观测三件套接线要点：应用暴露指标端点供 Prometheus 抓取；日志输出到 stdout 且为结构化 JSON；链路数据按 OTLP 发给 Collector 或直接给 Jaeger。三者都要在 README 给出「打开哪个地址看什么」。
- 性能优化报告的结构：基线环境 → 压测方法（并发、时长、数据量）→ 优化前数据 → 定位手段（pprof / trace / 指标）→ 优化项与代码位置 → 优化后数据 → 副作用与代价。
- 干净环境验证记录模板：环境（OS/容器运行时/CPU 内存）→ 步骤序号 → 命令 → 耗时 → 是否踩坑 → 修复动作 → 已回写到 README 的哪一节。
- `docs/pitch.md` 的 5 分钟结构建议：30 秒问题与用户 → 60 秒架构与关键决策 → 120 秒两个技术深挖 → 60 秒数据与验证 → 30 秒不足与后续计划。
- 高频追问清单的必答项：为什么不用现成框架、缓存与数据库如何保持一致、消息重复消费怎么办、CPU 限流与 `GOMAXPROCS` 的关系、GC 参数为什么这么设、故障时的降级行为、数据指标怎么采集的。
