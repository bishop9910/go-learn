## 2. 提交规范

每个作业一个独立目录，放在你自己的练习仓库里（不是本仓库）：

```text
go-learn-work/
├── LEARNING-LOG.md
├── hw00-environment/
├── hw01-cli-skeleton/
├── hw02-stdlib-cli/
└── ...
```

每个作业目录必须包含：

| 项 | 要求 |
| --- | --- |
| `README.md` | 用法、验收命令、设计说明、已知限制 |
| 代码 | 能 `go build ./...` 通过 |
| `go.mod` | 每个作业独立 module，不要互相 import 本地路径（除非作业要求） |
| 测试 | `go test ./...` 全绿；涉及并发的必须 `go test -race ./...` 全绿 |
| `SELF-REVIEW.md` | 按作业的评分表逐项自评打分，并写明扣分理由 |
| 提交记录 | Git 提交信息能说清做了什么（不要一条 `update` 提交全部） |

## 3. 评分标准

每份作业满分 100 分，权重表在各自作业文件中给出。通用的判定口径：

| 维度 | 说明 | 常见扣分点 |
| --- | --- | --- |
| 功能正确性 | 需求项逐条实现，边界与错误路径都覆盖 | 只做 happy path；忽略并发与超时 |
| 工程结构 | 分层清晰、依赖方向正确、无包级全局状态 | 所有代码堆在 `main.go` |
| 错误处理 | 包装、判定、翻译三层分明；错误不被丢弃 | `_ = err`；用字符串比较判断错误 |
| 测试 | 覆盖关键路径与失败路径，有可解释的覆盖率 | 只测 happy path；测试之间共享状态 |
| 文档 | 与实现一致，能让人按文档跑起来 | 文档写的是上一版实现 |
| 可观测性 | 有结构化日志，关键路径有耗时与结果 | 用 `fmt.Println` 调试 |
| 版本准确性 | 使用的 Go 特性标注了版本要求 | 把 Go 1.27 的写法当成 1.25 可用 |

**一票否决项**（出现任一条，本作业按不通过处理）：

1. `go build ./...` 或 `go test ./...` 失败。
2. 明文存储或传输密码。
3. 提交了密钥、`.env`、生产连接串。
4. `go vet ./...` 有报错，或 `gofmt -l .` 输出非空。
5. 涉及并发的作业 `go test -race` 报出竞争。
6. 直接复制他人项目代码且无法解释关键设计。

## 4. 通用技术要求

从 hw01 起长期有效：

- Go 版本基线 **1.25**；使用 1.26 / 1.27 的特性必须在 `README.md` 与代码注释里标注版本，并确认本机工具链满足。
- 每个作业都必须有 `README.md`，且 README 里的命令是**真的能跑**的。
- 日志一律用 `log/slog`，禁止用 `fmt.Println` 做应用日志。
- 测试优先表格驱动；涉及时间的逻辑优先用 `testing/synctest`（Go 1.25 转正）而不是真实 `time.Sleep`。
- 第三方库只写模块路径，不写死版本号；提交前用 `go mod tidy` 收敛依赖。
- 网络受限时固定 `GOTOOLCHAIN=local`，避免 go 命令尝试下载工具链。

## 5. 怎么用「参考实现要点」

每份作业的最后一节是「参考实现要点」，它只给关键设计决策与关键代码片段。使用方法：

1. **先自己写**，卡住超过 40 分钟再去看。
2. 看的时候只对比「设计决策」，不要照抄代码结构。
3. 如果发现自己的方案与要点不同但更合理，**保留自己的方案并在 `SELF-REVIEW.md` 里论证**——这比照着抄更有价值。

## 6. 与阶段门的关系

阶段门（G0–G6，见 [plan/00-overview.md](../plan/00-overview.md)）的通过条件是「该阶段全部作业自评 ≥70 分 + 阶段性综合验收清单全部打勾」。

作业通过但阶段门未过，说明作业之间的整合出了问题（典型症状：每个作业单独能跑，但拼不成一个服务）。这时要做的是**补齐整合**，而不是继续往下做。
