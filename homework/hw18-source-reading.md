## 1. 背景与目标

把「会用」升级为「知道为什么」。本作业要求**带着问题读**标准库源码：每个问题都要落到具体入口函数与关键分支，并且必须有一个可运行的验证程序把结论固定下来。产物是一份 `reading-report.md` 加一组验证程序。

允许读官方文档、Release Notes 与标准库注释，但结论必须由本机源码与程序输出支撑。

## 2. 需求（必须项）

1. MUST 报告开头写明所用 Go 版本（本机基线 `go1.25.7`；若已升级须写明新版本）与源码路径（`go env GOROOT`），并声明「不同版本源码可能不同，以下结论对应的版本是 X」。
2. MUST 每条结论附齐四要素：源码文件与函数名、可运行的最小验证程序、观察到的输出、与官方文档或 Release Notes 的对照。
3. MUST 路径一（`net/http` 服务端一次请求的完整路径）：`Server.Serve` → 连接处理 → `conn.serve` → 路由匹配 → handler 调用 → 响应写出；回答「Go 1.22 起增强 `ServeMux` 的模式匹配优先级如何实现」（标注 1.22+）与「中间件为什么能包裹 handler」。
4. MUST 路径一追问：`ResponseWriter` 什么时候才真正写头（哪些条件会触发隐式写出状态行与头部）。
5. MUST 路径二（连接复用与客户端）：`Transport` 的连接池结构、`MaxIdleConnsPerHost` 如何生效、`Response.Body` 不读完为什么不能复用连接；并用源码与实验验证 Go 1.27 起 HTTP/1 的 `Response.Body` 关闭时自动排空未读内容的行为及其保守上限（标注 1.27+）。
6. MUST 路径三（`context`）：`cancelCtx` 的传播结构（为什么是树形）、`Done()` channel 的惰性创建、`WithValue` 的链式查找成本、`WithCancelCause` 与 `Cause`（1.20）的实现、`AfterFunc`（1.21）的实现要点。
7. MUST 路径三附一项测量：用程序测量深层 `WithValue` 的查找开销，给出「深度 vs 单次查找耗时」数据表。
8. MUST 路径四（`sync`）：`Mutex` 的正常模式与饥饿模式、`TryLock` 的语义、`WaitGroup` 的计数器与信号量设计、`WaitGroup.Go`（Go 1.25 新增）在源码中如何实现（标注 1.25+）、`sync.Pool` 的 per-P 私有槽与 victim cache、`Once` 与 `OnceFunc`。
9. MUST 路径五（`channel`，作为加分内容的必读替代可放附录）：有缓冲与无缓冲 `hchan` 结构、发送/接收等待队列的组织、`select` 随机公平性的实现。
10. MUST 至少推翻或修正一个自己原先的直觉：如实记录「原以为 → 实际是 → 是哪个实验/哪段源码纠正的」。
11. MUST 附录给出版本差异对照表：哪些行为在 1.25、1.26、1.27 之间发生了变化，每条注明来源（Release Notes 链接或源码位置）。
12. MUST 所有验证程序可独立运行并打印结论，且每个程序至少包含一个成立用例与一个对照用例。

## 3. 需求（加分项）

1. 用 `go doc` 或 `go doc -http`（Go 1.25+）配合源码定位交叉验证结论。
2. 画出至少两张结构图（如 `Transport` 连接池、`cancelCtx` 树）并说明图中每个字段的来源函数。
3. 用 `runtime/metrics` 中新增的 goroutine 相关指标（Go 1.26 起，见 <https://pkg.go.dev/runtime/metrics>）观察 `WaitGroup`/`context` 验证程序的 goroutine 变化。
4. 用 `testing/synctest`（Go 1.25 转正：`synctest.Test`、`synctest.Wait`）写一个确定性并发验证，替换不可靠的 `time.Sleep`。
5. 找出至少一处标准库注释与当前实现不完全一致的地方，并给出证据（此类发现很有价值，找不到也可如实说明）。

## 4. 技术约束

- 结论必须基于本机 `GOROOT` 源码，不得以博客转述作为证据。
- 引用源码位置必须精确到文件与函数名；若给行号，须注明对应的 Go 版本。
- Go 1.26/1.27 才有的行为不得声称在 1.25 上验证通过；反之亦然。
- 验证程序总运行时间控制在一分钟内，便于助教复跑。
- 不得把 `unsafe` 当捷径绕过问题；确需使用时必须说明理由。
- 第三方依赖不作为证据来源。

## 8. 提示与思路

- 阅读顺序建议：先读类型定义与结构体注释，再读入口函数，最后读边界分支（错误处理、超时、取消）。跳过结构定义直接读流程会反复迷路。
- 定位入口的技巧：从导出 API 反向找调用点，例如先找 `Serve`，再顺着它调用的连接处理方法往下走；用编辑器的跳转比手动翻文件快得多。
- 「`ResponseWriter` 何时真正写头」这类问题，靠读代码容易漏分支，最有效的做法是写一个自定义 handler，在写头前后打印状态，再构造「只写 body」「先写头再写 body」「只设头不写 body」三种情况做对照。
- `context` 的树形传播可以用一个小程序验证：创建父子链后取消中间节点，观察两侧 `Done()` 的关闭顺序（用 `select` 非阻塞读取判断是否已关闭）。
- `sync.Pool` 的行为必须用「取不到时新建 + 统计命中」的方式测，不要假设它一定保留对象；观察 GC 前后命中率的变化最能说明问题。
- 纠正直觉的记录要写清「当时为什么这么想」（通常来自某篇博客或某个 API 名字的暗示），这比结论本身更有价值。

## 9. 常见坑

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| 只看博客不看源码 | 结论无法定位，遇版本变化即失效 | 每条结论落到 GOROOT 中的文件与函数 |
| 把注释当实现 | 注释描述的语义与当前代码不一致 | 以代码分支为准，注释只做辅助 |
| 忽略版本差异 | 拿 1.27 行为解释 1.25 程序 | 标注版本，附录给出对照表 |
| 结论没有验证程序 | 无法自证，也无法回归 | 每个结论配一个最小程序 |
| 把「读到一段代码」当「理解机制」 | 报告变成代码摘抄 | 必须回答「为什么必须是这个结构」 |
| 结论过度泛化 | 把 HTTP/1 的结论套到 HTTP/2 | 明确限定协议版本与配置前提 |
| 验证程序依赖 `time.Sleep` | 结果偶发不稳定 | 用 channel 同步或 `testing/synctest` |
| 行号写死不留版本 | 换版本后引用全错 | 行号必须带版本标注 |

## 10. 参考实现要点

- 报告的固定小节模板（每条路径复用）：

```text
### 问题 N：<一句话问题>
- 入口：<文件:函数>
- 关键分支：<分支条件与走向>
- 结论：<可被验证的断言>
- 验证：verify/<program>.go，输出：<粘贴真实输出>
- 对照：<官方文档 / Release Notes 链接>
- 版本：<该结论适用的 Go 版本范围>
```

- 验证程序的统一骨架：`main` 中先跑「预期成立」的用例，再跑「对照组」，最后打印 `PASS/FAIL` 与关键数值，退出码非 0 表示结论不成立。
- `WithValue` 查找开销的测量方法：构造深度 1/8/64/512 的链，每档循环足够多次取平均值，报 `ns/op` 量级与增长趋势，并说明这台机器的噪声水平。
- `Transport` 连接复用的验证方法：用本机服务端统计连接建立次数（服务端侧的连接状态回调或自建计数器，API 名称以 `net/http` 官方文档为准），对照组分别是「读完 body 并关闭」「只读一部分就关闭」「Go 1.27+ 下只读一部分就关闭」。
- `WaitGroup.Go` 的源码阅读要点：它本质是把「计数加一 + 启动 goroutine + 完成时减一」收敛为一个方法，从而规避 `Add` 位置写错的问题（Go 1.25 的 `go vet` 也新增了 `waitgroup` 检查，Go 1.27 起该分析器更名为 `waitgroupgo`）。
- 附录版本对照表建议只收录与本次阅读直接相关的条目，例如增强 `ServeMux`（1.22）、`WithCancelCause`/`Cause`（1.20）、`AfterFunc`（1.21）、`WaitGroup.Go`（1.25）、`Response.Body` 关闭时排空（1.27）。
