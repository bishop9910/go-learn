## 1. 背景与目标

hw11 交付的是一个单体 gRPC 服务：调用被换成了 RPC，但服务仍然只有一个部署单元，依赖地址写死在配置文件里，任何参数改动都要重启进程。本作业把它拆成 `user-service` 与 `post-service`，并补齐拆分带来的两个基础设施缺口：**服务之间怎么找到彼此**（注册与发现），以及**参数怎么在不重启的前提下变更**（配置中心）。

目标：

1. `post-service` 通过 gRPC 调用 `user-service` 获取作者信息，先以静态地址跑通，再切换为动态发现，业务代码不变。
2. 实例上下线对调用方透明：正常退出与 `kill -9` 两种情况下，都不再往失效实例发请求。
3. 白名单内的参数变更后 3 秒内对全部在线实例生效，且配置中心不可用时已有实例继续正常工作。
4. 用一次真实的故障演练，写清「注册中心挂了」这一场景下系统的实际行为边界，而不是停留在设计意图。

## 2. 需求（必须项）

**M1 服务拆分与契约。** 拆出 `user-service` 与 `post-service` 两个可独立启动、独立构建、独立部署的进程，各自拥有独立数据库；`post-service` 不得直接读写用户表。接口契约先用 `.proto` 定义再生成代码，字段编号遵守「只加不删、不复用」的兼容规则。

**M2 静态地址打通。** 第一版用写死的 `host:port` 让 `post-service` 调通 `user-service`，提交这个可运行版本，并记录下它在「实例重启后地址变化」时会出现的具体错误。

**M3 服务注册。** 进程启动完成后，把自身实例信息注册到注册中心：服务名、地址、端口、版本、健康状态。注册动作必须在「可以接收流量」之后执行，不能先注册再初始化。

**M4 优雅注销与租约续期。** 收到退出信号后，先注销实例、等待在途请求结束，再退出；进程被强杀时靠租约（lease）或 TTL 心跳过期自动清理。心跳间隔、租约 TTL、健康检查超时三个数值要一起给出并说明推导依据。

**M5 脏节点清理。** 写一个演示脚本：`kill -9` 一个实例后，记录注册中心里该节点从「存在」到「消失」的耗时，以及这段时间内客户端是否仍可能选中它、系统如何兜底。

**M6 服务发现与 watch。** 客户端从注册中心拉取实例列表并订阅变更，实现热更新；订阅连接断开必须自动重连，并在重连后重新拉取一次全量列表（不能只依赖增量事件）。

**M7 客户端负载均衡。** 实现轮询策略，并至少再实现「最少连接」或「随机」中的一种；策略可通过配置切换。

**M8 连接级与请求级均衡的说明。** 在 README 中解释：为什么 gRPC 长连接场景下 L4 负载均衡不够用，连接级均衡与请求级均衡的差异，以及本实现属于哪一类。

**M9 健康检查。** 暴露健康端点（`grpc_health_v1`，包路径见 <https://pkg.go.dev/google.golang.org/grpc/health/grpc_health_v1>；或自建 HTTP 健康端点），并区分「进程存活」与「就绪（可以接流量）」。注册中心中的健康状态必须与就绪状态联动。

**M10 故障实例摘除。** 当健康检查或调用探测判定某实例不健康时，立即把它从负载均衡池摘除，不等 TTL 过期；恢复后要能重新加入。写测试证明「池中剩余 2 个实例时，100 次调用全部成功且不落在被摘除的实例上」。

**M11 配置中心接入。** 用 `etcd` 或 `Consul` 存配置（二选一，并在 README 用一页说明取舍依据）。服务启动时拉取全量配置。

**M12 配置热更新。** 订阅配置变更，变更后 3 秒内生效，读路径不阻塞、不重启进程，且 `go test -race ./...` 无数据竞争。

**M13 本地缓存与降级。** 配置落盘或内存缓存；配置中心不可用时，用「上一次成功拉取的配置」正常启动并打 WARN 日志，不允许因为拉不到配置就 panic 或阻塞启动。

**M14 配置版本与回滚。** 每次变更记录版本号，支持把生效版本指回上一个版本并触发一次热更新。

**M15 热更新白名单。** README 中列出「允许热更新」与「必须重启」两类参数清单，逐条给出理由；白名单之外的参数即使被改动也不得生效。

**M16 故障演练记录。** 停掉注册中心，观察并记录三件事：已启动实例是否继续正常处理请求；新实例启动是失败还是降级、降级后表现如何；把注册中心恢复后系统多久自愈。

**M17 测试。** 覆盖三项：两个服务的集成测试（含一次跨服务调用）；负载均衡策略单测（3 个实例、100 次调用，验证分布符合预期并打印实际分布）；配置热更新单测（写入新版本后读到的值发生变化，解析失败时保留旧值）。

**M18 README。** 含架构图（服务、注册中心、配置中心的连接关系）、一次调用的完整链路说明（从客户端发起到 `post-service` 拿到作者信息返回，逐跳标注）、选型取舍、演练结果。

## 8. 提示与思路

1. **先做静态版本，再替换。** 把依赖抽象成一个接口（例如 `UserClient`），静态实现与发现实现都满足它，切换只改装配代码一行。这样 M2 的产物不会被丢弃。
2. **注册与就绪是两个时刻。** 常见做法是：监听端口成功 → 依赖初始化完成 → 健康检查返回就绪 → 然后才写注册中心。紧接着注册失败也不应让进程崩溃，而是重试并保持未就绪。
3. **watch 必须假设会断。** 断线、超时、注册中心重启都会让订阅失效，重连后重新拉全量是最省心的正确做法。
4. **配置读路径用原子快照。** 一个 `atomic.Pointer[Config]` 字段即可让读路径无锁，写路径（watch 回调）解析并校验成功后再替换指针；校验失败就保留旧快照。
5. **白名单是设计的一部分。** 「哪些参数允许热更新」比「怎么热更新」更容易出错：凡是需要重建连接池、重新监听端口、重新协商 TLS 的参数，一律走重启。

## 9. 常见坑

| 坑 | 现象 | 根因 | 正确做法 |
| --- | --- | --- | --- |
| 只注册不注销 | 注册中心里节点越积越多，请求间歇性打到死实例 | 退出路径没有注销，或先于注销就被强杀 | 收到信号先注销，租约 TTL 兜底强杀场景 |
| 心跳间隔与健康检查超时打架 | 实例在「健康」与「不健康」之间反复横跳 | 心跳周期大于 TTL，或探活超时小于正常处理时间 | 让 TTL 明显大于心跳间隔，超时留足余量并给出计算 |
| watch 断线不重连 | 新实例上线后调用方永远看不到 | 只处理了一次事件流就退出 | 事件流循环退出即重连，重连后重拉全量 |
| 配置热更新引发数据竞争 | `-race` 报错或偶发读到半个配置 | watch 回调直接改被并发读的字段 | 不可变快照 + 原子指针替换 |
| 实例列表存在包级变量 | 多服务实例或多次测试互相污染 | 全局可变状态 | 每个客户端持有自己的列表，靠订阅更新 |
| 服务名大小写与路径不一致 | 注册时写 `UserService`、查询时写 `user-service`，永远查不到 | 服务名没有单一常量来源 | 服务名定义为一处常量，注册与发现共用 |
| 先注册后初始化 | 新实例注册后立刻收到请求并大量报错 | 注册时机早于就绪 | 就绪检查通过后再注册 |

## 10. 参考实现要点

**配置快照：读无锁、写校验。** 这一段是 M12/M13 的核心，其余都可以围绕它组织。

```go
type Config struct {
	RequestTimeoutMS int
	LogLevel         string
	FeatureFlag      map[string]bool
}

type Store struct {
	snap atomic.Pointer[Config] // 读路径只做一次 Load，无锁
}

func (s *Store) Load() *Config { return s.snap.Load() }

// apply 由 watch 回调调用：解析或校验失败必须保留旧快照
func (s *Store) apply(raw []byte) error {
	var c Config
	if err := parseAndValidate(raw, &c); err != nil {
		return err
	}
	s.snap.Store(&c)
	return nil
}
```

关键设计决策：

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 配置读取 | 原子指针快照 | 读路径无锁，热更新不影响请求延迟 |
| 校验失败处理 | 丢弃新配置、保留旧值 | 一次手误不应让全部实例崩溃 |
| 注册时机 | 就绪之后 | 避免把流量引到没准备好的实例 |
| 摘除方式 | 主动标记 + 立即生效 | 等 TTL 过期意味着一段时间的确定性失败 |
| 降级数据来源 | 上一次成功的持久化配置 | 启动时不必依赖注册中心在线 |

负载均衡单测的建议形态：用假的实例列表构造 3 个实例，跑 100 次选择，断言每个实例被选中的次数落在期望区间内（轮询应严格为 34/33/33 一类的确定分布），把实际分布打进 `t.Log`，便于人工核对。

验收时的取舍说明要诚实：如果故障演练中发现「注册中心不可用时新实例确实起不来」，就写「起不来」，不要为了好看改成「自动降级」。
