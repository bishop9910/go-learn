## 1. 背景与目标

hw12 的两个服务已经能互相调用，但同步调用把可用性和延迟绑在了一起：发一篇文章要同步等索引、摘要、通知三件事全部完成，任何一件慢都会拖住用户。本作业在 `user-service` 与 `post-service` 之间引入消息队列，把这三件事改为异步，并解决随之而来的核心问题：**数据库写成功而消息丢失**，以及**消息重复投递导致业务重复生效**。

目标：

1. 文章发布只依赖一次本地事务：业务表与 `outbox` 表在同一事务内写入，事务提交即代表「业务成功且消息一定会被投递」。
2. 同一消息投递两次，业务结果只生效一次，并用测试证明。
3. 同一文章的多个事件保持有序，异步链路中不出现乱序。
4. 失败可重试、可进死信、可人工重放，全过程有日志与埋点位置。

## 2. 需求（必须项）

**M1 消息队列选型。** 在 `Kafka`、`NATS`（含 JetStream）、`RabbitMQ`、`Redis Stream` 中任选其一，README 中给出取舍说明（投递语义、顺序性保证、运维成本、本地可用性四个维度）。Go 客户端只写模块路径并注明「以官方最新稳定版为准」，例如 `github.com/twmb/franz-go`、`github.com/segmentio/kafka-go`、`github.com/nats-io/nats.go`、`github.com/rabbitmq/amqp091-go`、`github.com/redis/go-redis`。

**M2 异步业务链路。** 用户发布文章后，异步完成三件事：更新搜索索引、生成摘要、给关注者发通知。三个消费者各自独立，任一失败不影响另外两个。

**M3 先落库再发消息。** 业务表与 `outbox` 表在同一个数据库事务内写入；不得出现「落库成功但消息丢失」。禁止在事务提交之前投递消息，也禁止把投递失败当成业务失败回滚。

**M4 Outbox 表结构。** 给出迁移脚本，字段至少覆盖：主键、聚合标识（文章 ID）、事件类型、事件负载、状态、重试次数、可用时间、创建时间、发送时间。为「按状态 + 可用时间扫描待发送记录」建立索引，并说明为什么这个索引的前缀顺序是这样。

**M5 中继（relay）。** 独立 goroutine 或独立进程轮询 `outbox` 并投递到 MQ，成功后标记为已发送。README 说明：为什么按 `id` 或 `created_at` 有序推进；如何避免重复投递（同一行被两个中继实例同时取走）；如何避免堆积（批量大小、轮询间隔、并发投递上限）。

**M6 幂等消费。** 消费者必须幂等：用「业务唯一键 + 去重表」，或用「状态机 + 版本号做乐观并发」。写测试证明「同一消息投递两次，业务结果只生效一次」，并断言第二次被识别为重复。

**M7 顺序性。** 至少一个场景要求同一文章的多个事件有序（例如「文章创建」必须先于「文章更新」被处理）。README 说明分区键的选择，并实现「按 key 路由到固定 worker」的机制，保证同一 key 串行。

**M8 生产者确认与提交位移时机。** 生产者使用确认机制；消费者在处理成功之后才提交位移，处理失败不提交。README 明确指出本实现属于「至少一次」投递，并说明重复从何而来。

**M9 重试与死信。** 失败重试采用指数退避并带抖动；超过次数上限后进入死信队列。给出死信处理与人工重放流程：如何查看死信内容、如何修复后重放、重放时幂等如何保证。

**M10 可观测性。** 用 `log/slog` 输出结构化日志，至少覆盖消费积压、消费延迟、失败次数三类信号。指标本轮先留出埋点位置（函数与字段命名到位），在 hw14 接入 Prometheus，本作业不引入指标依赖。

**M11 补偿事务。** 给出一个 Saga 或补偿事务的例子，例如「生成摘要失败则把文章的摘要状态标记为失败并允许重试」。说明补偿操作本身的幂等性要求，以及补偿失败时的处理办法（进入人工介入队列，而不是无限重试）。

**M12 测试。** 覆盖三项：`outbox` 写入与业务写入的同事务性（事务回滚时 `outbox` 不留记录）；幂等消费者的重复投递测试；重试与死信的单元测试（用假的失败注入，不依赖真实 MQ）。

**M13 文档。** README 含消息流时序图、投递语义说明（至少一次/至多一次/恰好一次，本实现是哪种、代价是什么）、失败处理策略表（失败类型 → 是否重试 → 退避策略 → 最终去处）。

## 8. 提示与思路

1. **把「投递」当成状态机而不是一次函数调用。** `pending → sending → sent`，或者更简单的 `pending → sent` 加乐观并发；关键是任何一步崩溃后重启都能继续推进。
2. **幂等键要选业务唯一键。** 例如用「文章 ID + 事件类型 + 事件版本」构造唯一约束，让数据库来保证唯一，而不是靠先查后写的竞态判断。
3. **分区键决定顺序边界。** 以文章 ID 作为分区键，同一文章的事件天然落在同一分区；再按分区键哈希到固定 worker，就得到串行处理。
4. **重试要区分可重试与不可重试。** 数据库连接抖动可重试，字段校验失败不可重试——不可重试的错误直接进死信，比重试到上限更省时间。
5. **补偿不是回滚。** 补偿是一个新的前向操作，它只保证业务语义上收敛，因此必须自己幂等；补偿失败要留人工入口。

## 9. 常见坑

| 坑 | 现象 | 根因 | 正确做法 |
| --- | --- | --- | --- |
| 先发消息后落库 | 数据库回滚了但消息已发，消费方读到不存在的文章 | 投递在事务之外且早于提交 | 同事务写 `outbox`，中继负责投递 |
| `outbox` 与业务表不同事务 | 偶发「有业务无事件」或「有事件无业务」 | 两次独立写入 | 同一事务、同一数据库连接 |
| 消费者自动提交位移 | 处理还没结束位移就提交，进程崩溃后消息永久丢失 | 位移提交时机错误 | 处理成功后手动提交，失败不提交 |
| 把 MQ 当数据库查询 | 消费方反复消费历史消息做查询 | 缺乏读取模型 | 需要查询就落库，MQ 只做事件通道 |
| 重试无上限 | 一条坏消息把消费者卡死，积压无限增长 | 没有次数上限与死信 | 上限 + 退避 + 死信队列 |
| 事件里塞整个实体 | 上游一加字段就影响所有消费者，schema 僵化 | 事件与实体耦合 | 只放消费方需要的字段，事件带版本号 |
| 消费并发破坏顺序 | 同一文章的「创建」出现在「更新」之后 | 无 key 路由，多 worker 抢同一分区 | 按 key 哈希到固定 worker |
| 去重表没有唯一约束 | 并发下两条重复消息同时通过检查 | 先查后写存在竞态 | 唯一索引 + 插入冲突即视为重复 |

## 10. 参考实现要点

**Outbox 与业务写入同事务。** 下面是最小骨架，重点是两次写入共用一个事务对象。

```go
// 事务相关 API 见 database/sql：https://pkg.go.dev/database/sql
// 业务写入与事件写入必须在同一个事务内提交
func (r *PostRepo) CreateWithEvent(ctx context.Context, tx *sql.Tx, p Post, ev Event) error {
	if _, err := tx.ExecContext(ctx, insertPostSQL, p.ID, p.AuthorID, p.Title, p.Body); err != nil {
		return err
	}
	// 事件只写"事实"，不写消费方的派生结果
	_, err := tx.ExecContext(ctx, insertOutboxSQL,
		ev.ID, ev.AggregateID, ev.Type, ev.Payload, StatusPending, 0, ev.AvailableAt)
	return err
}
```

**中继的有序推进与抢占。** 每一次循环只推进游标，不回头扫描已完成区间。

```text
每轮：
  1. SELECT ... FROM outbox
       WHERE status = 'pending' AND available_at <= now()
       ORDER BY id LIMIT :batch            -- 按 id 有序，游标只前进
       FOR UPDATE SKIP LOCKED;             -- 多中继实例不抢同一行
  2. 逐条投递；成功置 sent，失败置 pending 并 attempts+1、available_at 后移
  3. attempts 超过上限置 dead，等待人工重放
```

关键设计决策：

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 扫描顺序 | 按 `id` 升序、游标只前进 | 保证同一聚合的事件按写入顺序投递 |
| 多实例并行 | 行锁跳过已占用行 | 不重复取行，且不需要额外的分布式锁 |
| 失败退避 | 指数退避 + 抖动 | 避免同一时刻整批重试造成尖峰 |
| 顺序与并发的边界 | 按分区键哈希到固定 worker | 同 key 串行、不同 key 并行 |
| 补偿的幂等 | 状态机带版本号，条件更新 | 重复补偿不改变最终状态 |

可观测埋点先留位置，hw14 再落地：`outbox_pending`（积压）、`consumer_lag_seconds`（消费延迟）、`consume_failed_total`（失败次数）。本作业只要求把这些值写进 `slog` 字段，例如每轮中继结束打一条含 `pending_count` 的 INFO 日志。
