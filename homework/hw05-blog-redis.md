## 1. 背景与目标

hw04 解决了「谁在调用」，本作业解决「数据怎么存、怎么查、怎么缓存」。你要在 MySQL 之上实现文章与标签的多对多模型，把列表查询跑在正确的索引上，再用 Redis 做 Cache-Aside，并让整个读路径在缓存失效或 Redis 宕机时仍然正确。

完成本作业后你应能：

- 从查询出发设计索引，并用 `EXPLAIN` 证明索引被使用。
- 说出缓存穿透、击穿、雪崩的触发条件、后果与各自的解法边界。
- 解释「先更新 DB 再删缓存」的时序与不一致窗口，并给出兜底。
- 让缓存成为可选依赖：Redis 不可用时接口退化而不是返回 500。

## 2. 需求（必须项）

**数据模型与迁移**

- **M1** 必须有以下表及其关系，字段类型与约束在迁移文件中显式声明：

| 表 | 关键字段 | 约束 |
| --- | --- | --- |
| `users` | `id`、`email`、`created_at` | `email` 唯一 |
| `posts` | `id`、`author_id`、`title`、`body`、`status`、`created_at`、`updated_at` | `status` 取值 `draft` / `published`；`author_id` 外键指向 `users` |
| `tags` | `id`、`name`、`slug` | `slug` 唯一 |
| `post_tags` | `post_id`、`tag_id` | 联合主键，两个外键；删除文章时级联清理 |

- **M2** 迁移必须可重复执行：同一份迁移连续跑两次不报错、不产生重复数据（用版本表或幂等 DDL 二选一，README 说明方案）。
- **M3** 列表查询必须走索引，不得出现全表扫描。README 附上至少两条 `EXPLAIN` 的真实输出（`sql` 代码块），并指明命中的索引名与预估扫描行数。

**接口**

- **M4** 必须实现下列端点：

| 方法 | 路径 | 认证 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/v1/posts` | 是 | 创建文章，可带 `status` 直接发布 |
| GET | `/api/v1/posts` | 否 | 列表，支持标签、作者、状态筛选与分页 |
| GET | `/api/v1/posts/{id}` | 否 | 文章详情；草稿仅作者可见 |
| PATCH | `/api/v1/posts/{id}` | 是 | 更新标题、正文、状态 |
| DELETE | `/api/v1/posts/{id}` | 是 | 删除文章 |
| GET | `/api/v1/tags` | 否 | 标签列表 |

- **M5** 分页必须实现 `page`/`size` 或游标两种之一，并在 README 说明取舍（深翻页成本、结果稳定性、能否跳页）。参数必须有上限校验，`size` 超过上限时返回 400。
- **M6** 资源级授权：非作者不可修改或删除他人文章，返回 403；草稿对非作者返回 404 或 403（二选一并保持一致）。必须有一个用例专门证明无法通过猜测 `id` 越权（防 IDOR）。
- **M7** 列表与详情响应必须使用独立的响应 DTO，不得直接序列化数据模型。

**Redis 缓存**

- **M8** 使用 `github.com/redis/go-redis/v9`（以官方最新稳定版为准）。所有 Redis 调用必须带 `context.Context` 且设置超时，禁止使用无超时的后台 context。
- **M9** 必须实现 Cache-Aside：详情缓存、列表缓存（带 TTL 抖动）、写路径更新 DB 成功后删除相关缓存。
- **M10** README 必须给出 key 设计表，列至少包含：key 模板、语义、数据结构、TTL、失效时机。

| key 模板 | 语义 | 结构 | TTL |
| --- | --- | --- | --- |
| `<ns>:post:{id}` | 文章详情 | 字符串 | 10 分钟 + 抖动 |
| `<ns>:list:{filter_hash}` | 某组筛选条件的列表页 | 字符串 | 60 秒 + 抖动 |
| `<ns>:tags` | 标签列表 | 字符串 | 5 分钟 |

- **M11** 三大缓存问题至少处理两个，README 逐项写明触发条件、后果、实现位置（文件与函数）：
  - 穿透：不存在的 `id` 也要缓存空值，且给更短的 TTL。
  - 击穿：热点 key 失效瞬间用 `golang.org/x/sync/singleflight`（以官方最新稳定版为准）收敛为一次回源。
  - 雪崩：TTL 加随机抖动，避免批量同时失效。
- **M12** README 必须画出「先更新 DB 再删缓存」的完整时序图（`text` 代码块），并回答三个问题：为什么不用「先删缓存再更新 DB」、不一致窗口有多长、TTL 上限如何兜底。
- **M13** 删缓存失败不得影响写接口的成败：写接口返回成功，删缓存失败只记日志与指标；给出补偿思路（重试或延迟双删二选一）。

**降级与测试**

- **M14** Redis 不可用时读接口必须回源数据库并正常返回，不得 500；写接口同样不得因删缓存失败而失败。
- **M15** 必须有一个测试模拟 Redis 超时或连接失败（可用测试替身或指向不可达地址），断言接口仍返回 200 且响应体正确。

## 8. 提示与思路

- **先跑 `EXPLAIN` 再写代码**：把列表查询的 SQL 手写进客户端跑一次，确定索引组合（例如按 `status` + `created_at` 的复合索引），再让仓储层实现它。
- **缓存键要能算出来**：列表缓存 key 用「筛选条件规范化后的哈希」而不是原始 query 字符串，避免参数顺序不同导致缓存碎片。
- **把缓存封装成接口**：让 service 依赖一个缓存接口而非具体客户端，测试注入假实现即可精确断言命中与回源。
- **删除而不是更新缓存**：写路径只删 key，让下次读重建，可少一次并发写入的竞争面。
- **先写降级测试**：把「Redis 挂了」当成一等需求写测试，能反向逼出正确的错误处理与超时配置。

## 9. 常见坑

| 坑 | 现象 | 根因 | 正确做法 |
| --- | --- | --- | --- |
| 缓存与 DB 双写不一致 | 更新后读到旧数据 | 先更新缓存或更新与删缓存顺序混乱 | 先更新 DB 再删缓存，并靠 TTL 上限兜底 |
| TTL 不设 | 数据永久陈旧，内存只增不减 | 认为缓存可以永久有效 | 每类 key 都设 TTL，并按热点程度分级 |
| key 无命名空间 | 多服务共用实例时互相覆盖 | key 用裸 `id` 或裸邮箱 | 统一前缀 + 业务段 + 版本段 |
| 大 key | 单次读写阻塞、网络抖动被放大 | 把整表或整个列表塞进一个 key | 分页片段化，单 value 设上限 |
| 连接池配满 | 高峰期排队、超时激增 | 池上限与数据库承载能力不匹配 | 显式配置池大小与空闲回收，压测验证 |
| `go-redis` 的 context 超时 | 偶发长尾，Redis 慢时请求拖死 | 用无超时或长超时的 context | 每个调用带短超时，并纳入全局请求预算 |
| 缓存空值不分情况 | 数据库故障被缓存成「不存在」 | 把查询失败也当成空结果写入 | 只缓存确认不存在的结果，查询失败直接返回错误 |

## 10. 参考实现要点

- **过期时间集中管理**：把每类 key 的 TTL 定义成常量表，抖动由同一个函数生成（在 `base*(1-ratio)` 到 `base*(1+ratio)` 之间取值），避免 TTL 计算散落在各处；随机源必须是并发安全的。
- **Cache-Aside 读路径顺序**：查缓存 → 命中且为空值标记则按不存在处理 → 未命中则经 singleflight 回源 → 回源成功写入缓存（不存在的写入短 TTL 空值）→ 回源失败不写缓存并返回错误。
- **写路径顺序（时序图要点）**：

```text
写请求 → BEGIN → 更新 posts/post_tags → COMMIT（成功）
      → 删除 <ns>:post:{id} → 删除相关 <ns>:list:* → 返回 200
      （删缓存失败：记日志 + 指标，不改变写接口结果；由 TTL 上限兜底）
```

- **不使用「先删缓存再更新 DB」的理由**：删除后到事务提交之间存在窗口，并发读会把旧值重新写回缓存，反而延长不一致；写库成功后再删，配合 TTL 能把不一致窗口控制在一次缓存未命中的时间内。
- **降级实现形态**：用一个包装层把缓存调用包起来，超时或连接错误统一转成「未命中」语义并打点；上层只判断命中/未命中，不感知 Redis 是否存在。
- **集成测试建议**：每个用例前清空相关 key 并在事务中准备数据；用「先写库、再置缓存」的显式步骤验证命中与未命中，不要依赖测试执行顺序。
- **自检**：README 里的每个 key 都能在代码中 grep 到；停掉 Redis 的全部接口仍能返回正确数据；列表查询的 `EXPLAIN` 输出与 README 一致。
